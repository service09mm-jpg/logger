# Архітектура і правила роботи

Цей документ існує з двох причин. По-перше, власник проєкту вчить Next.js і
JavaScript по ходу справи, тому код має бути читабельним для людини, яка знає
синтаксис, але не знає фреймворк. По-друге, більшість коду пише агент, і йому
потрібні межі, які не дають «на всяк випадок» переписати половину застосунку.

## Про Clean Architecture без фанатизму

Вимога — чиста архітектура за Мартіном. Беремо з неї те, що справді працює на
цьому масштабі, і свідомо не беремо церемонію.

**Беремо — Dependency Rule.** Бізнес-логіка не знає нічого про фреймворк. Функція,
яка рахує прогрес до цілі, не повинна здогадуватись про існування React, Prisma
чи HTTP. Це найцінніше правило Мартіна і водночас найдешевше у виконанні.

**Не беремо — чотири кільця, DI-контейнер, інтерфейси репозиторіїв із окремими
реалізаціями, мапери між шарами.** У застосунку на три таблиці це додає сотні
рядків, які нічого не захищають: ми ніколи не мінятимемо Postgres на щось інше, і
абстракція заради гіпотетичної заміни — це чистий податок. Мартін сам пише, що
кількість шарів не догма.

Підсумок: **три шари замість чотирьох, і жорстке правило залежностей замість
формальних інтерфейсів.**

## Структура

Головна вимога — щоб зміна в одній частині застосунку не тягнула за собою правки
в непов'язаних. Тому ділимо спершу **за фічами**, і лише всередині фічі — за
шарами. Це протилежність до поділу «всі компоненти в одну папку, всі хуки в іншу»,
де будь-яка задача розповзається по всьому дереву.

```
src/
  features/
    metrics/           # усе про метрики: створення, шаблони, налаштування
      domain/          # чистий TypeScript: правила, обчислення, типи
      data/            # єдине місце, де ця фіча торкається Prisma
      ui/              # React-компоненти цієї фічі
      index.ts         # ПУБЛІЧНИЙ API фічі — тільки через нього ззовні
    entries/           # усе про записи: ввід, редагування, заднім числом
    targets/           # усе про цілі та прогрес
    charts/            # календар, лінійний графік, стовпчики
  shared/
    i18n/              # словники uk/en
    ui/                # кнопки, шторка, numpad — без доступу до БД
  lib/
    prisma.ts          # клієнт Prisma, єдиний екземпляр
  app/                 # Next.js App Router: роути й Server Actions, тонкі
```

Поточний стан репозиторію — скафолд: існують лише `src/app/` і
`src/lib/prisma.ts`. Дерево вище — цільове, воно наповнюється в міру появи фіч, а
не створюється порожніми папками наперед.

### Правило залежностей

Стрілка означає «може імпортувати»:

```
app  →  features/*/ui  →  features/*/data  →  features/*/domain
                                                      ↑
                                        не імпортує НІЧОГО з проєкту
```

Конкретно:

- **`domain/` не імпортує нічого** — ні `react`, ні `next`, ні `@prisma/client`,
  ні сусідні шари. Це просто TypeScript-функції над простими типами. Саме тут
  живе логіка агрегації, меж періоду й перевірки цілі.
- **`data/` імпортує `domain/`** і Prisma. Більше Prisma не з'являється ніде.
- **`ui/` імпортує `domain/` і `data/`**, рендерить React.
- **`app/` тонкий**: дістає юзера, викликає фічу, віддає розмітку. Логіки в
  роутах немає.
- **Між фічами — тільки через `index.ts`.** `features/charts` не лізе в
  `features/metrics/data/metricRepo.ts`, він бере те, що `features/metrics`
  експортує назовні.

### Чому саме так, якщо коротко

Логіка, яку цікаво читати й вчити, опиняється у файлах, де немає ні Next.js, ні
React, ні SQL — просто функції з іменами й типами. Їх можна відкрити, зрозуміти й
покрити тестами, не знаючи фреймворку. А весь фреймворк-специфічний шум
зосереджений у тонкому шарі `app/`, який робить мало.

### Межі мають бути машинними, а не на чесному слові

Правило, записане лише в документі, агент рано чи пізно порушить — не зі зла, а
тому що в його контексті цього документа може не бути. Тому правило залежностей
виражене в `eslint.config.mjs` і перевіряється в CI: порушення валить збірку, а
не тоне в рев'ю. Зараз машинно заборонені чотири речі:

| Де | Що не можна | Чому |
| --- | --- | --- |
| `features/*/domain/` | імпортувати React, Next, Prisma | шар мусить лишатись чистим TypeScript |
| `features/*/domain/` | імпортувати `../data/`, `../ui/` | залежності йдуть лише вниз |
| будь-де в `src/` | `@/features/<фіча>/<підпапка>` | у чужу фічу — тільки через її `index.ts` |
| `app/` | імпортувати Prisma напряму | роути ходять у базу лише через `data/` |

Помилка лінтера містить пояснення, а не лише код правила — щоб зрозуміти її можна
було без відкривання цього файлу.

## Конвенції коду

Пишемо для читача, який знає синтаксис, але не знає ідіом.

- **Ніякого «розумного» JavaScript.** Простий цикл кращий за ланцюжок
  `reduce`/`flatMap`. Проміжні результати отримують імена замість того, щоб
  збиратись в один вираз на пів екрана.
- **Явні типи повернення в усіх експортованих функціях.** Сигнатура має читатись
  як документація, без наведення мишкою.
- **Тільки іменовані експорти**, без `export default` — так їх видно грепом.
- **Один змістовний експорт на файл**, файл названо за ним.
- **Без скорочень** в іменах: `calculateProgress`, не `calcProg`.
- **Коментар пояснює «чому», а не «що».** Окремо — коментар там, де вжито
  специфічну для Next.js чи React ідіому: один рядок про те, що саме тут
  відбувається і навіщо.
- **Серверні й клієнтські компоненти позначені явно**, і в клієнтських перший
  рядок файлу пояснює, чому цей компонент мусить бути клієнтським.
- **TypeScript `strict`**, `any` заборонений.

## Тести

Юніт-тести Vitest покривають `domain/` — саме там живуть усі правила, і саме там
тест читається як специфікація. Вони не потребують ні React, ні бази, ні знання
фреймворку.

`data/` і `ui/` тестуються вибірково, e2e Playwright — тільки для двох сценаріїв
гарячого шляху: створити метрику й залогувати значення.

**Зміна в `domain/` без тесту не приймається.**

## Як працює агент

1. **Одна задача — одна фіча — один PR.** Задача формулюється як «фіча
   `entries`: додати редагування запису», і агент править файли **тільки
   всередині цієї фічі** плюс, за потреби, `shared/`.
2. **Вихід за межі фічі — це зупинка, а не рішення.** Якщо агент вважає, що треба
   зачепити сусідню фічу чи змінити її публічний API, він **зупиняється й
   питає**, а не робить це сам. Це головне правило: більшість шкоди приходить не
   з поганого коду, а з правок у місцях, яких задача не стосувалась.
3. **Розмір PR — орієнтир 300 рядків діфу.** Більше — ділимо. PR, який неможливо
   прочитати за один присід, не виконує своєї навчальної функції.
4. **Опис PR має три частини:** що змінилось, чому саме так, і **з якого файлу
   починати читати**. Третє — не формальність: це те, що перетворює рев'ю на
   навчання.
5. **Рефакторинг не їде разом із фічею.** Побачив щось, що варто переписати —
   окремий PR, окремий опис.
6. **Не додавати залежність без питання.** Кожна нова бібліотека — це те, що
   власнику проєкту доведеться вчити.
7. **Не чіпати того, чого не просили** — конфіги, CI, форматування чужих файлів,
   версії пакетів.

## Що робити, коли правило заважає

Правила тут не священні, але змінюються явно: спершу правка цього документа
окремим PR, потім код за новим правилом. Мовчки зробити виняток — найгірший
варіант, бо наступного разу ніхто не згадає, чому так.
